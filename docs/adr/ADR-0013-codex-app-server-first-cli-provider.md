# ADR-0013: Use local-stdio Codex App Server for the first CLI provider

Status: accepted

## Context

The first real provider needs a documented, stable control surface for bounded
launch, active-run input, observation, cancellation, and artifact collection.
It must not rely on terminal UI automation, remote-desktop control, a public
listener, or embedded credentials. The selected protocol will be implemented
only in the next Roadmap slice; this ADR does not install, authenticate, or run
Codex on any host.

## Options reviewed

| Surface | Documented strengths | Decision |
| --- | --- | --- |
| Codex `exec` | Explicit sandbox, JSONL events, and a final structured output path. | Not selected: its non-interactive shape is completion-oriented and does not expose active-turn steering. |
| Codex App Server | Local JSON-RPC over stdio; explicit threads, turns, streamed items, `turn/steer`, `thread/read`, and `turn/interrupt`; version-specific TypeScript and JSON schemas can be generated by the installed CLI. | Selected as the first provider protocol. |
| Claude Code print/stream mode | Documented stream JSON, background sessions, stop operations, and queued stdin messages. | Keep as a candidate second CLI provider so the shared boundary is tested against an independent implementation. |
| Gemini CLI headless mode | Documented JSON/JSONL results and exit codes. | Not selected: its documented non-interactive Plan Mode transitions implementation to YOLO, which is not an acceptable default for this bounded provider. |

## Decision

The initial provider is `codex-app-server`, launched only as one local child
process per approved run with `codex app-server --listen stdio://`. No WebSocket
or other listening endpoint is permitted. A future implementation opens a
JSONL stdio session, sends `initialize`, then uses `thread/start` and
`turn/start` with a policy-approved working directory and bounded provider
configuration.

Lifecycle mapping:

| AgentOps lifecycle | Codex App Server operation | Boundary |
| --- | --- | --- |
| capability inspection | local version/schema discovery and manifest construction | No auth, task, or provider launch is implied by declaration. |
| environment validation | validate protocol version and approved local executable reference | No credential value is read or stored. |
| start | `thread/start` then `turn/start` | Only after the Worker/Coordinator policy and signature boundary accepts the job. |
| send input | `turn/steer` for an active turn; later completed-turn input creates a new turn only through the durable Coordinator path | Input is a typed, redacted provider invocation, never raw shell transport. |
| inspect | normalized streamed item events plus `thread/read` | Raw provider transcripts are not operational truth. |
| pause and resume | unsupported | The manifest must declare both explicitly; no process suspension is implied. |
| cancel | `turn/interrupt`, then collect bounded evidence before ending the local process | Cancellation is observable and never silently restarts work. |
| collect artifacts | bounded changed-file, diff, command-result, and final-message references | Secret values, raw auth state, and unbounded transcripts are excluded. |

The implementation must use a local stdio-only transport and an injected child
process/JSON-RPC port. It must not use `--listen ws://`, `--listen wss://`,
`--yolo`, a bypass-approval flag, UI automation, remote desktop, or a raw API
key environment assignment. Human or service authentication is an external,
private, separately authorized enrollment concern.

## Test-double design

The test kit now has `ScriptedJsonRpcTransport`: an in-memory ordered JSON-RPC
transcript double. It proves `initialize`, start, active-turn steer, inspection,
and interruption correlation without a Codex binary, network connection,
credential, or process. The following implementation slice must add the
adapter on top of that port and prove provider conformance, unexpected protocol
output refusal, crash/recovery, cancellation, and artifact redaction.

## Consequences

- The first provider is a provider-specific adapter only; generic job and
  domain contracts remain vendor-neutral and capability-routed.
- Claude Code is deliberately retained for a later second-provider proof; no
  task can name either provider unless a human explicitly expresses a valid
  preference after capability and policy filtering.
- This decision authorizes repository code and deterministic fixtures only. It
  does not authorize executable installation, authentication, provider launch,
  host service changes, cloud configuration, or remote-access changes.
